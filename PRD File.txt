1. Executive Summary
Project Goal: To build a high-performance, custom-coded website for "Soldiers of Jesus Christ" that serves as a digital home for the congregation, a powerful evangelism tool for newcomers, and a streamlined administrative hub for church leadership.
Target Audience: Local community members seeking a church home, current members seeking community and resources, and online viewers seeking spiritual content.
Core Mission: "Equipping the Saints for the Battle. Standing Firm in Faith."
 
2. Visual Identity & "The Vibe"
Based on the provided design reference, the website will break away from traditional, outdated church designs and adopt a modern, high-converting aesthetic.
•	Color Palette:
o	Primary: Deep Navy Blue (#0A1D37) – Represents authority, stability, and the uniform of a soldier.
o	Secondary: Gold/Yellow (#F5A623) – Represents victory, royalty, and the glory of God.
o	Neutral: Crisp White (#FFFFFF) and Light Gray (#F4F4F4) – For clean backgrounds and readability.
•	Typography:
o	Headings: Bold, commanding sans-serif (e.g., Montserrat, Oswald, or Inter). Use uppercase for emphasis.
o	Body: Clean, highly legible sans-serif (e.g., Open Sans or Roboto).
•	Imagery: Authentic, high-resolution photos of the congregation, worship sessions, and community outreach. Avoid generic stock photos. Images should be slightly darkened with overlays to ensure white text pops.
•	UI Elements: Sharp, modern cards with subtle drop shadows. Gold buttons with hover effects (e.g., slight scale-up or darkening).
 
3. Recommended Tech Stack (Custom Code)
Since you are coding this from scratch, here is the best modern stack for scalability, SEO, and speed:
•	Frontend Framework: Next.js (React) – Provides Server-Side Rendering (SSR) for excellent SEO, fast page loads, and dynamic routing.
•	Styling: Tailwind CSS – Perfect for implementing the card grids, responsive layouts, and custom color palette efficiently.
•	Backend: Node.js with Express OR Next.js API Routes (Serverless functions).
•	Database: PostgreSQL (via Prisma ORM) – Robust for managing events, sermon metadata, and member data.
•	Headless CMS: Sanity.io or Strapi – Allows church staff to update sermons, events, and team bios without touching the code.
•	Authentication (Optional): NextAuth.js – For a member portal or volunteer login.
•	Hosting: Vercel (Frontend/API) + Render (Database).
 
4. System Architecture
•	Client Layer: Web Browser (Desktop/Mobile), Mobile App (future).
•	Frontend Layer: Next.js App Router, Tailwind CSS, React Components.
•	API Layer: Next.js API routes handling requests for Giving (Stripe), YouTube (Data API v3), Forms (SendGrid/Mailchimp), and Events.
•	Database Layer: PostgreSQL storing Events, Sermon Metadata, User Profiles, and Form Submissions.
•	External Integrations:
o	Stripe/PayPal: For secure online giving.
o	YouTube Data API v3: Automatically pulls the latest sermons.
o	Google Maps API: For location and directions.

ADMIN PANEL EXPANSION & ARCHITECTURE
1. Admin System Architecture
•	Route Structure: The admin panel will live on a separate route: https://yourdomain.com/admin.
•	Security: This route must be protected by Middleware. If an unauthenticated user tries to access /admin, they are immediately redirected to a login page (/admin/login).
•	Authentication: NextAuth.js. We will use a Credentials Provider (Email + Password) and optionally Google OAuth.
•	Authorization (RBAC): Not all admins should have all power. We will implement Role-Based Access Control:
o	SUPER_ADMIN: Full access (can manage users, delete records, view financials).
o	EDITOR: Can manage sermons, events, and content, but cannot view giving reports or manage users.
o	VIEWER: Can only view data (e.g., prayer requests) but cannot edit or delete.
•	Server Actions: Use Next.js Server Actions to handle form submissions (creating events, adding sermons) securely on the server side, eliminating the need for excessive API routes.
2. Core Admin Features & Workflows
The admin panel will be split into 7 key modules:
1.	Dashboard Overview:
o	Quick stats: Total donations this month, upcoming events, unread prayer requests.
o	Quick actions: "Add New Event", "Post Latest Sermon".
2.	Sermon Manager:
o	Form to add a new sermon: Title, Speaker, Series, Date, YouTube Video ID.
o	Toggle to "Feature on Homepage".
3.	Event Manager:
o	Create, Edit, Delete events.
o	View event registrations and export attendee lists to CSV.
4.	Giving & Financials:
o	View transaction history (synced via Stripe Webhooks).
o	Filter by date, fund, or amount. Export reports.
5.	Form Submissions (Inbox):
o	A unified inbox for Contact Forms, Prayer Requests, and "I'm New" cards.
o	Mark as "Read", "Replied", or "Archived".
6.	Content Management (CMS):
o	Edit the Homepage Hero text (Headline, Subheadline, CTA links).
o	Edit the About Us and Beliefs pages without code.
7.	User Management (Super Admin only):
o	Invite new admins, change roles, revoke access.

4. Updated Database Schema (Prisma)
We need to add models for users and update existing models to support admin workflows.
prisma
// Add to schema.prisma

enum Role {
  SUPER_ADMIN
  EDITOR
  VIEWER
}

model User {
  id        String   @id @default(cuid())
  name      String
  email     String   @unique
  password  String   // Hashed
  role      Role     @default(EDITOR)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}

enum EventStatus {
  DRAFT
  PUBLISHED
  CANCELLED
}

model Event {
  id          String      @id @default(cuid())
  title       String
  description String
  date        DateTime
  location    String
  image       String
  status      EventStatus @default(DRAFT)
  registrations Registration[]
}

model Sermon {
  id        String   @id @default(cuid())
  title     String
  youtubeId String
  speaker   String
  series    String?
  date      DateTime
  featured  Boolean  @default(false)
}

enum SubmissionType {
  PRAYER_REQUEST
  CONTACT
  NEW_MEMBER
}

model FormSubmission {
  id        String         @id @default(cuid())
  type      SubmissionType
  name      String
  email     String
  message   String
  isRead    Boolean        @default(false)
  createdAt DateTime       @default(now())
}
